# 动态软件组合与可逆运行时

## 定义与边界

研究组件在运行时被加载、卸载、替换和重配置时，如何恢复其可归属的状态修改，并按依赖拓扑协调其他组件生命周期。边界只覆盖能由运行时经 context key reify、追踪并提供逆的 acquisition；网络发送、持久化写入等 emission 不自动可逆。

## 为什么重要

Self-evolving agent harness、插件生态、热模块替换和服务滚动更新都需要细粒度变更，而进程重启会丢失缓存、连接和进行中的任务。可逆运行时把清理责任从每个插件作者提升为组件抽象，但也把正确性前提集中到 inverse、依赖图和接口设计上。

## 2026-09-29 增补：恢复的对象决定契约

[[notes/papers/2026/09/29/OpenAI4S- Code as Action, Science as Sessions]] 将恢复对象推进到科学研究会话：worker 内的 Python/R namespace、workspace、版本产物与执行环境。与 [[notes/papers/2026/08/31/Logos- An Agent Harness on a Cross-Process Bus]]、[[notes/papers/2026/08/31/EvoUndo- Recoverability-Constrained Self-Evolution for LLM Agent Harnesses]] 结合看，需要分开三种操作。

| 操作 | 要恢复什么 | 机制 / 验证 | 仍不能保证什么 |
| --- | --- | --- | --- |
| 组件卸载或 mutation 撤销 | effect contract 所定义的前态 | 可逆 acquisition、witness/undo、反事实状态验证 | 外部 emission 自动可逆；并发变更不被覆盖 |
| 会话跨进程接续 | durable transcript 对应的执行前缀 | Logos 的持久记录、call/result 配对、故障注入 | 第三方已提交副作用在未知窗口中的 exactly-once |
| 科学 kernel 重建 | checkpoint 对应文件、需要的符号、产物和环境 | OpenAI4S 的候选 worker、hydrate、受限 replay、hash/environment 检查 | 任意对象序列化；新机器重建；科学结果正确 |

OpenAI4S 的 replay 只选择满足安全、成功、依赖与环境条件的 cell，覆盖不足时报告 partial/failed；自动 checkpoint 是 best-effort，背景 worker 不继承前台 namespace（§3.2–3.3，pp.4–6；补充 S1/S4，pp.18–19）。这与本主题的 emission 边界一致：重放历史代码不等于撤销外部世界变化，也不应该重复不可逆操作。

**证据强度**：Logos 现有笔记记录 controlled crash tests；EvoUndo 记录反事实恢复实验；OpenAI4S 本轮仅核对论文与 pinned source 的 validate-before-publish 路径，论文总体跑分没有单独测量恢复机制贡献。三者不能按总分横向排名。

**个人设计推断**：统一恢复接口至少应声明恢复对象、covered effects、版本/环境、不可重放步骤、验证证据和未恢复部分。先定义成功契约，再决定用 inverse、transcript 接续还是 cell replay；避免把“能看到旧结果”标为“计算状态完全恢复”。

- [ ] 在同一小工作流中分别注入 worker crash、文件版本冲突和不可逆外部调用，验证三种恢复契约的覆盖边界。
- [ ] 检查 replay 被拒绝时是否能保留已捕获产物，同时明确标记缺失 namespace。

## 核心问题

1. 哪些 Agent 状态/工具调用可以安全归属到一个组件并撤销？
2. provider 替换时，如何保证 consumer 不读到混合版本或悬空依赖？
3. 如何验证逆函数、操作交换性和跨语言接口兼容，而不是把它们当作作者承诺？

## 方法谱系

| 路线 | 代表论文 | 核心假设 | 优势 | 局限 |
| --- | --- | --- | --- | --- |
| Revertible effects + reactive coeffects | [[notes/papers/2026/08/31/A Programming Paradigm for Spatiotemporal Composability]] | context 内修改可提供逆；依赖按 key 可解析 | 细粒度卸载、依赖驱动生命周期、可证明合流 | 无自动 witness 检查；边界外 emission 不可逆；无性能基线 |
| 手写 cleanup / compensation | OSGi、插件生命周期、Saga | 作者实现正确 teardown | 易接入现有系统，能处理外部副作用 | 遗漏 cleanup 会泄漏；顺序与依赖难审计 |
| 进程/服务级重启 | Kubernetes、监督树 | 粗粒度隔离足够 | 工具成熟，故障边界清晰 | 丢失进程态、恢复慢、共享地址空间组件无法独立替换 |
| State-forward migration | DSU、Webpack/Vite HMR | 旧新版本间存在迁移函数 | 可保留组件状态 | 需要手写迁移；不适合彻底卸载 |

## 当前共识

- 动态组件的“恢复”必须区分 context 内 acquisition 与不可撤销 emission。
- provider/consumer 生命周期顺序应由依赖解析驱动，而不是要求 orchestrator 手工安排全序。
- 组件级合流通常需要比单组件回滚更强的独立性、接口和依赖图条件。

## 关键争议

- `revertible effects` 的作者提供 inverse 是否足够，还是应由类型系统、运行时日志或形式化验证强制检查？
- key identity、peer dependency 和 structural compatibility 如何组合，才能避免跨包 interface drift/key collision？
- 对自进化 Agent，频繁替换带来的状态迁移需求是否会抵消“撤销后重建”的简单性？
